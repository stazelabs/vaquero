- **No migration.** No task adds one. If one seems needed, stop and report.
- **Workflows:** never add `push`, `pull_request` or `pull_request_target` triggers (a test holds it). Pin every action by full SHA with the tag in a comment (a test holds it). Workflow changes are verified only by running them, so say exactly what to check.
- CLAUDE.md and `.claude/rules/*` are edited only by the controller. Subagents write `claude-md-task-N.patch` in the run workspace.
- Never touch port 7878, the owner's data directory (`~/Library/Application Support/vaquero`), the owner's brew service, or `~/Library/LaunchAgents`. Tests use temp dirs and injected paths, and manual checks use port 7881 with a temp `VQ_DATA_DIR`. Reading Homebrew's own source under `$(brew --repository)/Library/Homebrew` is fine (read only).
- Gate, each step separately by exit code: `make gen`, `make fmt`, `make vet`, `make lint`, `make test`; then `make ci`. Commits `{Area}: {summary} (VAQ-N)` with the Co-Authored-By line, only the paths changed (never `git commit -a`). Dependency versions match startcase; add no Go dependency.

## Review Focus

1. **An upgrade under `brew services` on macOS** (VAQ-123): with the service file named `sh.brew.vaquero.plist`, the CLI defers to brew. It never stops the service's server or starts its own, and `vaquero stop` refuses with the brew hint.
2. **A custom `VQ_DATA_DIR` is never treated as the service's** (VAQ-120, still holding R4 from the last run), including on Linux when the shell's and the systemd manager's `XDG_DATA_HOME` differ.
3. **Status order** (VAQ-126, 125): a new status lands at the end of its category. A claim still moves a ticket to the first in-progress status. The board's columns follow the order. Every change has its one event.
4. **Logs** (VAQ-121, 58): rotation never loses lines and works when stdout and stderr are files the service manager opened. `vaquero logs` finds the right file without a server.
5. **Narrow screens** (VAQ-30, 31): checked by hand in Chrome on :7881 at 375 px and 768 px, light and dark, with screenshots described in the report.

## Rulings (controller, 2026-11-25; the owner can overrule)

- **R1 (VAQ-123):** on macOS a service file is `~/Library/LaunchAgents/{homebrew.mxcl,sh.brew}.vaquero.plist`, either one. On Linux it is `~/.config/systemd/user/{homebrew,sh.brew}.vaquero.service`. Check against Homebrew's `services/formula_wrapper.rb` and `formula.rb` (`plist_names`, `service_names`) and match exactly. The wait in `startLocal` and the hint text use whichever was found. Tests cover both names on both systems, through an injected home and GOOS.
- **R2 (VAQ-120):**
  - **Linux XDG:** when the systemd user manager is reachable (`systemctl --user show-environment`, 2 s timeout, best effort), the default data directory for the service is computed from its `XDG_DATA_HOME`/`HOME`. Otherwise keep the current behaviour.
  - **`brew services run`:** also count the service when the service manager reports the label loaded (`launchctl print gui/$UID/{label}`; `systemctl --user is-active {unit}`), bounded at 2 s, for the default data directory only.
  - **Formula re-run:** a new manual workflow `.github/workflows/formula.yml` (`workflow_dispatch`, input `tag`) downloads `checksums.txt` from the existing release, renders the formula and pushes it. Move the publish shell out of `release.yml` into `scripts/publish-formula.sh` and call it from both workflows. RELEASING.md describes it. It is verified after merge by running it for v0.1.3, which should say the tap already holds this release's formula and change nothing.
- **R3 (VAQ-121, VAQ-58):**
  - **Rotation:** `backgroundLog` rotates when stderr is any regular file, not only `{data dir}/vaquero.log`. Same `logfile.Max`, one old file, and `Redirect` of fds 1 and 2.
  - **`vaquero logs [-n 100] [-f] [--path]`:** needs no server. It reads the brew service log (`{HOMEBREW_PREFIX}/var/log/vaquero.log`, the formula's `log_path`; take the prefix from the running executable's path, else `brew --prefix` with a 2 s timeout) when the service is detected for the default data directory, else `{data dir}/vaquero.log`.
  - `-f` follows across a rotation, and `--path` prints only the path.
  - Lines in the cli, installing-and-upgrading and data-and-backups articles.
- **R4 (VAQ-74, VAQ-60):** `CONTRIBUTING.md` as VAQ-74's decision says, and the README links it. One paragraph in the security help article as VAQ-60's decision says. VAQ-60 stays open on Phase 4; the controller notes that.
- **R5 (VAQ-126):** as the ticket says. Check `Claim`'s "first in-progress status" and the board against the new order.
- **R6 (VAQ-125, VAQ-127, VAQ-19):**
  - **Scope:** as the tickets say, with MCP tools out of scope.
  - **Core:** `MoveStatusTo(before|after)` is a new core call; the settings page's up and down buttons stay.
  - **Who:** any caller may make these changes. In local mode the token is the owner's, and agents are attributed through `Vaquero-Agent`.
  - **VAQ-19:** the settings form edits an existing milestone's description, through `UpdateMilestone`; extend it if it doesn't take a description yet.
- **R7 (VAQ-30, VAQ-31):**
  - **VAQ-30:** below `lg`, the milestone panel becomes a "Milestones" disclosure above the board, with the same filter links. It is a `<details>` element, so no inline script is needed.
  - **VAQ-31:** below `md`, an open rail overlays the active columns, with a close control and Escape to close (in app.js), instead of pushing them sideways. At `md` and up, behaviour is unchanged.
  - Theme tokens only, and no `style=`.
- **R8 (VAQ-122):**
  - **Symlinks:** `blobs.Location` resolves symlinks (`EvalSymlinks`) on both directories when they exist, falling back to Abs plus Clean. The recorded value for an unchanged setup stays the same.
  - **Sub-ticket tags:** read in one batched query (a new sqlc query by ticket ids).
  - **Bulk late cancel:** an item cut off after its last action fills `status` and `version` from the ticket that action returned.
