# CLAUDE.md

Guidance for working in this repo. Keep it short and current: edit it when an invariant or a product decision changes. Feature detail goes in the package's doc comment, not here.

## Summary

Vaquero is an agent-native, local-first, lightweight ticket tracker with coordination primitives for agents. One Go binary, one SQLite file. Local mode (one person, loopback) now; hosted mode (sign-in, cloud) from Phase 4. Design: docs/superpowers/specs/2026-11-18-vaquero-design.md. Plans: docs/superpowers/plans/ (Phase 0 foundation, Phase 1a core tracker, Phase 1b board, Phase 2a API and CLI, icons and help, Phase 2b agents, Phase 3a releases and upgrades, Phase 3b export, import and attachments). Releasing: docs/RELEASING.md. Work list: the VAQ project in the owner's own Vaquero (v0.1.0 on, through Homebrew at http://127.0.0.1:7878; `vaquero tickets VAQ`, `vaquero ticket show VAQ-N`). Each ticket is tagged by where it came from, and Phases 4 to 7 are milestones. File deferred work and open questions there as tickets, and move each ticket to done when it ships. docs/BACKLOG.md is the record up to Phase 3b; don't add to it. Never use a dev build or the test port against the owner's data directory. Infrastructure is ported from the sibling projects startcase and healthcheck-email (read-only); the porting reference is /Users/cstaszak/Stazelabs/projects/startcase/docs/superpowers/plans/2026-11-17-porting-map.md.

## Commands

    make tools     # one-time
    make gen       # templ + sqlc + tailwind (generated files are committed)
    make dev       # air hot reload on 127.0.0.1:7879 (7878 is a real vaquero's port); stamps version and commit like make build
    make test

Run `make` with no target to list every target; give each new target a `## description`.

Gate before every commit that touches Go, SQL, templ or CSS: `make gen && make fmt && make vet && make lint && make test`. Before gen inputs exist the gate is `make fmt vet lint test`. `make ci` adds `cover-check` (floors in coverage-floors.txt).

## Hard invariants

- Module `github.com/stazelabs/vaquero`; binary `vaquero`; `go 1.27.0`, `toolchain go1.27.3`; always `CGO_ENABLED=0`.
- Env prefix `VQ_`.
- Dependency versions match startcase's `go.mod`. No ORM, no cgo SQLite, no React, no validation library, no testify, no cobra.
- Licence Apache 2.0. Supported platforms for the local binary: macOS and Linux.
- `VQ_MODE=hosted` is refused at boot until Phase 4 adds sign-in.
- Local mode binds loopback only and rejects any request whose Host is not `localhost`, `127.0.0.1` or `::1`.
- IDs come only from `internal/idgen` (ULID). Instants are stored as text only through `internal/timefmt`.
- Writer pool has exactly one connection. Inside a transaction use `gen.New(tx)`, never the pool. Reads on request paths use the reader (`Deps.R`).
- CSP allows no inline script and no `style=` attribute. All behaviour is in `internal/web/static/js/app.js`.
- Templates use only the theme tokens; no raw hex or oklch values in `.templ` files.
- Generated files (`*_templ.go`, `internal/db/gen`, `tailwind.css`) are committed; `make gen && git diff --exit-code` must be clean.
- Documentation lives in `internal/help/articles` and ships in the binary; a new command, shortcut or API route needs its article line (tests enforce it). Icons are Lucide through `internal/web/icons`, never hand-drawn SVG.
- Copy: the product is "Vaquero" in prose and `vaquero` as a command. Sentence case, no exclamation points. Documentation and UI never name competing products.
- Local-first: everything works offline with the defaults; network services are optional and used only when the operator configures them. No telemetry; Vaquero never downloads or checks for releases.
- Never add `push` or `pull_request` triggers to GitHub workflows (`TestWorkflowsHaveNoPushOrPullRequestTriggers`).
- Commit messages: `{Area}: {summary}`.
- Only `internal/core` writes the tracker tables, and every successful change appends exactly one `events` row in the same transaction. Handlers read through `Deps.R` and write only through `Deps.Core`. The one offline exception is `vaquero import`, which fills a new database file with `archive.Load` before swapping it in; migrations may also rewrite rows (0008 backfills link event payloads); `blobs` is written only through `internal/blobs`.
- Agents: in local mode a request with the owner's token and a `Vaquero-Agent` header acts as that agent; other tokens ignore it. A ticket has at most one live claim; claims lapse, they are never silently stolen. MCP tools are API requests, never their own reads or writes.
- Tickets carry a `version` that rises on every change to the ticket; a save sent with an older version is refused (409 in the API, a banner on the web edit form, exit 3 in the CLI). Updates change only the fields they name.
- API tokens are stored as SHA-256 hashes with a 9-character prefix and shown once. Every API refusal is the same 401; never log a token.
- Upgrades go through Homebrew (`brew upgrade vaquero`) or a release archive; Vaquero never downloads or checks for releases. Releases are built by goreleaser from the manual `release` workflow (`.goreleaser.yaml`, no `brews`); the workflow then renders the Homebrew formula from `packaging/homebrew/vaquero.rb.tmpl` (with a `brew services` block) and `dist/checksums.txt` with `scripts/formula` (golden-file test) and writes `Formula/vaquero.rb` to `stazelabs/homebrew-vaquero` through `gh api`. Workflow actions are pinned to full commit SHAs with the tag in a comment (`TestWorkflowActionsArePinnedBySHA`). `VERSION` is the exact `v*` tag on HEAD, else `0.0.0-dev`.
- `testdata/upgrade/` holds a database from every release (`make fixture VERSION=X` before releasing); `TestFixturesMigrateToHead` migrates each to head and compares every value. Never edit, regenerate or delete a released version's fixture (an unreleased one is remade if a migration lands before its release; the release workflow checks the schema).
- One server per data directory (`vaquero.lock`). The local token lives in `{data dir}/token` (0600).
- Operator pages live under `/admin` inside `AdminShell` (home, API tokens, MCP activity).
- A project key can be changed in settings; the old key then stops resolving (ticket links, branch names and commit references using it break) and is free for another project. Ticket keys are `KEY-N`; URLs accept any case and leading zeros and redirect to the canonical form.
- Deleting a project, migrating on boot, restoring a backup, importing and compacting (`vaquero backup compact`) each take a database snapshot first (`{data dir}/backups`, newest `appdb.BackupKeep` = 7 of each kind kept); if the snapshot fails, nothing changes.
- Every page's footer carries "© 2026 Purple Bongo, Inc. · A Stazelabs project", the running version and links to `/about/licenses`. The logo is the cowboy hat (`static/logo.svg`, also the favicon).
- Departures from the siblings are deliberate: `internal/core` owns every mutation; passwords and passkeys (Phase 4); the CLI is an HTTP client (Phase 2).

## Rejected

mattn/go-sqlite3 (cgo), ORMs, gin/echo/fiber, React/Vite, Redis, validation libraries, testify, cobra, telemetry, Docker as a runtime requirement for local use.
